# 14 — Internationalization (i18n)

Viezan ships in three locales: **Vietnamese (vi)**, **English (en)** and **Japanese (ja)**. The system is intentionally tiny — no extra runtime dependency.

## Files

```
src/i18n/
├── index.ts                  t(), setLocale(), useLocale() (subscribes to Zustand)
├── types.ts                  Strict type for the locale object
└── locales/
    ├── en.ts
    ├── ja.ts
    └── vi.ts
```

The `Locale` type in `types.ts` is the contract. Adding or removing a key forces the TypeScript compiler to flag every locale that drifts.

## API

```ts
import { t, setLocale } from '@/i18n'

t('settings.apiKeys.title')                 // "API Keys"
t('chat.placeholder', { name: 'Hieu' })     // "Hi Hieu"
setLocale('ja')                              // persisted via settingsSlice
```

Locale state lives in `settingsSlice`:

| Field | Type | Default |
|---|---|---|
| `locale` | `'vi' \| 'en' \| 'ja'` | resolved from system |
| `localeAuto` | `boolean` | `true` |

When `localeAuto` is on, `App.tsx` calls `detectSystemLocale()` (`src/utils/locale.ts`) on mount and updates the store; manual selection turns the flag off.

## Key Conventions

- Dotted notation grouped by feature: `settings.apiKeys.title`, `translate.toolbar.style`, `live.actions.summarize`.
- One key per UI string. Don't reuse a key in semantically-different places (causes mistranslation).
- Parameters are passed as a flat object to `t(key, params)`. The replacement is `{name}` style.
- Pluralization is handled inline (`{count} item / {count} items`) — there is no ICU MessageFormat.

## Adding A Key

1. Add it to `src/i18n/locales/en.ts`.
2. Run TypeScript — `vi.ts` and `ja.ts` will fail to satisfy `Locale` until you add the same key.
3. Provide the translation in `vi.ts` and `ja.ts`. Don't ship a placeholder.
4. Use `t(key)` from any component (no provider needed).
5. The `audit-i18n-coverage` workflow can be run to confirm parity.

## No Hardcoded UI Strings

All user-facing text must go through `t(...)`. Common offenders to watch:

- `aria-label`, `placeholder`, `title` attributes.
- Toast / banner messages.
- Error fallbacks ("Something went wrong").
- Default chat / system prompt strings — these belong in locale files (or live in `chatSlice` if user-editable).

The `viezan-i18n-audit` skill / `audit-i18n-coverage` workflow searches for hardcoded UI text and missing keys.

## Chrome Extension Parity

The Chrome Extension has its own minimal copy of strings (no React, no shared bundle). When you change a user-facing string in the desktop app, mirror the change in:

- `chrome-extension/popup.html` / `popup.js`
- `chrome-extension/options.html` / `options.js`
- `chrome-extension/content.js` (floating button, tooltip)
- `chrome-extension/README.md`

## Locale Detection

`src/utils/locale.ts → detectSystemLocale()`:

1. Reads `navigator.language` (e.g. `vi-VN`).
2. Maps to one of `vi` / `en` / `ja` (default `en`).
3. Caches in `settingsSlice.locale`.

The `app:getInfo` IPC also returns `locale` from `app.getLocale()`, which is used by Quick Chat and the subtitle window where `navigator.language` may not be reliable.

## Subtitle Window

The subtitle overlay does not load the i18n bundle (kept minimal). It receives already-translated strings (`source`, `translated`) from the parent window via `subtitle:update`. Any UI text inside the overlay (e.g. "Click to dismiss") is hardcoded English in `public/subtitle.html` — this is an intentional exception.

## Quick Chat Window

Quick Chat is the same React bundle path as the main window, so `t(...)` works as usual. Locale is shared via the persisted store.

## Testing i18n

- TypeScript strictness on `Locale` covers structural parity.
- Vitest specs that snapshot UI sometimes pin the locale to `en` for deterministic output. Use `setLocale('en')` in `beforeEach`.
- Manual run: open Settings → Preferences → switch locale and walk through every page.
